## Army proposed decision (not implemented)

Smallest publisher-only option: a typed completed-retirement certificate can be recorded from the actual successful ObjectManager.Remove for Army, retaining original ID/handle and session identity. A guard may then distinguish known completed terminal cleanup from an unknown identity miss. However, because the original client destroy does not clear AiBehaviorObject, this alone is NOT a complete proven fix. No recommendation to drop all unknown Army messages, change logging severity, or globally move generic retirement.

More complete bounded candidate: an Army-only logical completion adapter keeps the original identity alive until the original outer MobileParty.Army setter operation finishes. It reuses the original InstanceDestroyed<Army> handler/wire once. ArmyRegistry's Army-specific destroy binding would be the only registry seam changed; the global factory/handler, ObjectManager and generated synchronization stay unchanged. Proposed new nongeneric adapter observes the original setter/disperse completion, tracks nested calls for that exact Army, and guards only a second Disperse in the same scope AFTER the first original Disperse completed successfully and actual terminal conditions hold. FinishArmyObjective, movement, tracking and ordinary setters continue normally. Release occurs after the outer setter's original/postfix callbacks; standalone disperse releases at its own complete boundary. Exceptions/partial cleanup/unknown or active objects do not obtain a retirement certificate or a successful completion. A faulted/pending scope cannot be treated as a handoff-safe state.

This scope is a proposed investigation implementation, not approved code and not proof that all native army removals fit the same outer boundary. Before selecting it, root must approve exact typed adapter and ArmyRegistry seam, including exception/unwind and cross-process test coverage. A successful server local cleanup is insufficient without proving the existing client destroy plus ordered field messages reaches the same terminal graph. The current original final-destroy pipeline remains unchanged in this review.

## PartyBase proposed minimal adapter (not implemented)

Use a type/graph-scoped identity-retirement lease, preserving every original reference message and original destroy handler. At the PartyBase-owned destroy seam of MobilePartyRegistry.OnServerDestroyed, defer ONLY when positive identity/handle belongs to the exact graph of an actively executing original first FinalizeEventAux on the current writer, and a concrete still-used side reference is verified. First scope should match the evidenced NPC garrison case, not all missing IDs or all IsFinalized events. Local native destruction, roster/casualty flush, selection and reward effects continue. This retains an existing identity briefly; it never invents a handle/re-adds a removed object.

Release through the original InstanceDestroyed<PartyBase> handler once AFTER the complete original FinalizeEventAux and all ordinary postfixes/subscribers (candidate nongeneric Harmony finalizer, with exact original exception propagation and first-call/original-ran proof). Then original field updates and parent MapEvent destroy have already been enqueued before the retained PartyBase destroy. The peer can resolve transient references, capture rewards and destroy the event graph before the final ordinary PartyBase identity retirement. Explicit release of each exact held PartyBase is mandatory because graph ownership excludes it.

The proposed late release must be tested against all handler queue boundaries. IsFinalized alone, an event notification alone, or a timeout must never release. Exception/unwind or an unresolved asynchronous write produces a faulted/pending lease and blocks acceptance/checkpoint, preserving original ERR/failure rather than silently discarding state. The existing cleanup can be reused; a blanket GenericHandler missing-reference exception, generator rewrite, early detachment or global ObjectManager retirement policy is unnecessary.

## Four required pre-change points and proposed seams

1. Existing functionality: mature generic lifetime registration/destruction and network destroy; Army native setters/events and typed client cleanup; MobileParty-owned identity cleanup; MapEvent original participant/reward/terminal graph ordering; immediate original AutoSync reference messages. All should remain in use.
2. Why current seams are insufficient: real successful removal receipts precede later valid native field writes on exactly the same object. Generic reference receive cannot recover an already deleted identity, and no completed-lifetime lease exists in current services. The solution belongs at typed lifetime boundaries. No evidence justifies rewriting generic registry, transport, generator, Mission owner/puppet or action/damage paths.
3. Invariants at risk: each logical destroy exactly once; source/value resolve while ordered references apply; original event/reward/movement/kingdom effects exactly once; no ID reuse/resurrection; client terminal equivalence; current-writer/Epoch and allowed-receive gates; no checkpoint of unresolved intermediate lifetime state; original exceptions preserved.
4. Required regression/native tests are below. None of these proposed adapters is implemented or accepted by this report.

Potential files for a separate approved task: new typed lifetime completion adapter/tests; ArmyRegistry.DestroyMethods only if the completion-scope option is selected; MobilePartyRegistry.OnServerDestroyed only for the exact PartyBase defer seam; existing finalization patch augmented via a separate nongeneric adapter. Preserve GenericHandler, AutoRegistryFactory, AutoRegistryHandler, LifetimePatches, ObjectManager, AutoSync templates and existing wire contracts. Names for a future ILifetimeCompletionDrain/lease service are PROPOSED, not existing APIs.
